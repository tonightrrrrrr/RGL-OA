## 1 项目概述

### 1.1 项目定位

本项目是一款在 Windows 本机离线运行的办公文件归档智能体。它批量接收本地办公文件，自动识别每份文件的所属部门、文件类型和生成日期，然后按规则重命名，归档到指定目录，并生成可以按关键词搜索、可以导出 Excel 的标准化文件目录台账。

### 1.2 设计原则

| 原则 | 含义 |
| --- | --- |
| 开箱即用 | 内置 Java 运行时和 OCR 模型，解压后双击运行，不需要安装 Java、数据库或 Python |
| 离线优先 | 核心功能不依赖网络，也不依赖大模型 API；文件不上传到任何外部服务 |
| 规则为主、模型为辅 | 规则引擎保证结果稳定、可解释；大模型只作为可选的复核手段 |
| 可解释、可追溯 | 每个识别字段都给出置信度和判断依据；置信度低时交给人工确认 |
| 不破坏原件 | 默认复制归档，原文件不动；每批操作都可以撤销 |
| 单点故障隔离 | 一个文件解析失败，不影响其他文件，程序不会崩溃 |

### 1.3 范围边界

本期包含：本地批量导入，Word、Excel、PDF、图片的解析与 OCR，部门、类型、日期识别，模板化重命名与归档，台账搜索与 Excel 导出，自定义 OA 模板，人工确认与撤销，Windows 绿色版和 Docker 两种交付方式。

本期不包含：多用户登录与权限、向量语义检索、与真实 OA 系统的接口对接、移动端、云端部署。

### 2.3 “智能体”的体现

处理过程做成“感知 → 推理 → 执行 → 反馈”的闭环，每个文件的每一步都写入处理记录（`process_step`），在界面上展示出来：

| 环节 | 能力 |
| --- | --- |
| 感知 | 解析多种格式，图片和扫描页自动走 OCR，检测印章 |
| 推理 | 文件名、锚点字段、标题后缀、词典、学习规则多路信号加权打分；配置了大模型时再让大模型复核 |
| 执行 | 按模板重命名、归档、生成档号、写入台账 |
| 反馈 | 置信度低的文件交给人工确认；用户修正后自动记成学习规则，下次遇到同类文件直接识别对 |

## 4 总体架构

### 4.1 部署形态

只运行一个进程。Spring Boot 内嵌的 Tomcat 同时提供 REST 接口和前端页面，H2 数据库和 OCR 引擎（通过 JNI 调用原生库）都在同一个进程里，浏览器访问 `http://127.0.0.1:<端口>` 即可。

```text
┌──────────────────────────── 浏览器（Vue 3 + Naive UI） ────────────────────────────┐
│  导入识别  │  待确认  │  台账  │  模板设置  │  系统设置                            │
└───────────────┬────────────────────────────────────────────────────────────────────┘
                │ REST（JSON）+ SSE（处理进度）
┌───────────────▼────────── OA-Archive-Agent.exe（单进程） ──────────────────────────┐
│ 启动器 Launcher：单实例 / 选端口 / 托盘 / 打开浏览器                               │
│ ┌─────────────────────────────── Spring Boot 3.5 ────────────────────────────────┐ │
│ │ Controller 层                                                                  │ │
│ │ ImportService → PipelineService ─┬─ ParserRegistry（POI / PDFBox / Tika）      │ │
│ │                                  ├─ OcrEngine（RapidOCR，可降级）              │ │
│ │                                  ├─ SealDetector                               │ │
│ │                                  ├─ RecognitionEngine（规则 + 学习规则）       │ │
│ │                                  └─ LlmReviewer（可选）                        │ │
│ │ ArchiveService（预览 / 执行 / 撤销）  LedgerService（检索 / 导出）             │ │
│ │ TemplateService  LearnedRuleService  SettingsService                           │ │
│ └────────────────────────────────────────────────────────────────────────────────┘ │
│ H2 文件库（data/db）   工作区（data/work）   日志（data/logs）                     │
└───────────────┬────────────────────────────────────────────────────────────────────┘
                │ 读源目录 / 写归档目录
        本地文件系统（源文件夹、归档根目录）
```

### 4.2 处理流水线

```text
导入 → 过滤 → 复制到工作区 → SHA-256 去重
  → 格式解析（Word / Excel / PDF / 图片 → OCR）
  → 文本清洗 → 统一文档模型（DocModel）
  → 区域切分：标题区 / 抬头字段区 / 正文 / 落款区 / 印章
  → 字段识别：部门、类型、日期、标题、扩展字段（多信号加权打分）
  → [可选] 大模型复核
  → 置信度判断：≥ 阈值 → 待归档；< 阈值 → 待确认
  → 生成新文件名、目标路径（预览）
  → 用户确认 → 执行归档 → 写入台账 → 记录操作日志（可撤销）
```

### 4.3 文件状态

```text
QUEUED → PARSING → RECOGNIZED ─┬─ READY（置信度达标）──┐
                               └─ REVIEW（待人工确认）─┴→ ARCHIVED → (UNDONE)
任一步出错 → FAILED（可重试）     哈希重复 → DUPLICATE（可强制归档）
```

### 4.4 线程模型

- 解析处理用独立线程池，大小为 `min(4, CPU 核数)`，每个文件是一个独立任务。
- OCR 用信号量限制并发（默认 2），防止大图片导致内存不足。
- 处理进度通过 SSE（Server-Sent Events）推送到前端。SSE 比 WebSocket 简单，也不需要额外依赖。

## 6 核心模块设计

### 6.1 文件导入

#### 6.1.1 导入方式

| 方式 | 实现 | 适用场景 |
| --- | --- | --- |
| 选择文件夹 | 后端弹出 Swing `JFileChooser`（只能选目录），返回所选路径 | Windows 绿色版的主要方式 |
| 手动填写路径 | 前端输入框 | 所有场景 |
| 拖拽上传 | 前端上传多个文件（`multipart/form-data`），保存到工作区 | 零散文件；Docker 版的主要方式 |
| 收件箱目录 | 扫描固定的 `inbox` 目录 | Docker 版通过挂载卷导入 |

浏览器出于安全限制，拿不到本地文件夹的真实路径。所以由后端弹出原生窗口来选择文件夹，这要求 Spring Boot 不以 headless 模式运行（见 6.10）。

#### 6.1.2 扫描与过滤

- 用 `Files.walkFileTree` 递归扫描，最大深度 10，不跟随符号链接。
- 跳过以下文件：`~$` 开头的 Office 临时锁文件、`.` 开头的隐藏文件、`Thumbs.db`、`desktop.ini`、0 字节文件、超过 200 MB 的文件（上限可配置）。
- 支持的扩展名：
  - 文档：`docx doc xlsx xls pdf txt rtf odt ods wps et`
  - 图片：`jpg jpeg png bmp tif tiff webp`
  - 其他扩展名交给 Tika 识别真实类型，能抽出文字就处理，否则标记为“不支持”。
- `.wps`、`.et`（WPS 私有格式）、`.webp` 的解析效果待 P2 阶段验证。

#### 6.1.3 工作区隔离

每个文件先复制到 `data/work/<batchId>/<fileId>.<ext>` 再解析。

原因有两个：第一，源文件被 Word 打开时处于锁定状态，直接读会失败（读示例文件时就遇到过）；第二，保证源文件在整个处理过程中都不会被改动。复制失败时，状态记为 `FAILED`，原因写“文件被占用”，可以重试。

#### 6.1.4 去重与异常隔离

- 计算 SHA-256。如果台账里已经有相同哈希的文件，状态标记为 `DUPLICATE`，界面上显示已有的那条记录，用户可以选择强制归档。
- 每个文件是一个独立任务，所有异常在任务内部捕获，写入 `error_message` 后继续处理下一个文件。
- 单个文件解析的超时时间为 120 秒（可配置），超时也记为 `FAILED`。

#### 6.2.1 统一文档模型

所有格式都转换成同一种结构，后面的识别逻辑只写一套：

DocModel（一份文件）：

| 字段 | 说明 |
| --- | --- |
| fileName / format / pageCount | 文件名、格式（docx、xlsx、pdf、image 等）、页数 |
| blocks | 文本块列表，按阅读顺序排列 |
| seals | 印章检测结果列表 |
| meta | 作者、创建时间等元数据 |

Block（一个文本块，即一段或一行）：

| 字段 | 说明 |
| --- | --- |
| text | 文字内容 |
| page | 所在页码，从 1 开始 |
| fontSize / fontName / bold | 字号（pt，无法获取时为 0）、字体、是否加粗 |

#### 6.2.2 各格式解析器

| 格式 | 解析器 | 获取的内容 |
| --- | --- | --- |
| docx | POI `XWPFDocument` | 段落文字（`getText()` 会合并同一段内的各个片段）、字号、字体、是否加粗、表格、页眉页脚、内嵌图片 |
| doc | POI `HWPFDocument` | 段落文字、字号 |
| xlsx / xls | POI `XSSFWorkbook` / `HSSFWorkbook` | 工作表名、单元格文字（按行列顺序）、表头行 |
| pdf | PDFBox `PDFTextStripper` 子类，开启 `setSortByPosition(true)` | 每行文字、坐标、字号（取 `TextPosition` 字高）；每页的字数；内嵌图片 |
| 图片 | OCR 引擎（6.3） | 文字块、坐标、置信度 |
| 其他 | Tika `AutoDetectParser` | 纯文本（没有字号和坐标） |

#### 6.2.3 文本清洗

| 规则 | 示例 |
| --- | --- |
| 删除中文与中文、数字之间多余的空格 | `2026 年 01 月 05 日` → `2026年01月05日` |
| 合并同字号的相邻行（只用于标题区） | `XXX有限公司 2026 年度第一次全体总经理` + `会议纪要` → 一行 |
| 全角转半角（只转数字、字母和冒号） | `２０２６` → `2026`，`：` 用于锚点匹配时视为 `:` |
| 合并连续的空行 | — |
| 保留脱敏占位符 | `XXX`、`***` 原样保留，不当作噪声删除 |

### 6.3 OCR 子系统（重点）

#### 6.3.1 OCR 是什么

OCR（Optical Character Recognition，光学字符识别）的作用是把图片里的文字转换成可以搜索、可以处理的文本。本项目使用 PaddleOCR 系列模型，处理分四步：

```text
原始图片
  ├─① 预处理：缩放、灰度化、分离红色通道
  ├─② 文字检测（DBNet）：找出每一行文字的位置，输出四边形框
  ├─③ 方向分类（AngleNet）：判断文字是否倒置 180°，倒了就转正
  └─④ 文字识别（CRNN）：识别每个框里的文字，给出置信度
        ▼
  [{ text:"签订日期：2025-12-25", box:[(x1,y1)…(x4,y4)], score:0.97 }, …]
```

坐标用来判断哪行是标题（页面上方、字最大）、哪几行属于落款区（页面下方）。这样 OCR 结果和 Word 文件能套用同一套识别规则。置信度用来决定是否交给人工确认。

#### 6.3.2 为什么必须用 OCR

1. 赛题明确要求：“通过文件名 + OCR 文本识别”，导入格式也包括“图片”。
2. 真实 OA 场景中常见扫描版的合同和批文、手机拍的签字页、截图和传真件。这些文件没有文字层，文件名也往往是 `扫描件001.pdf` 这种没有信息的名字。
3. 销售合同的印章是位图，盖章单位只能靠 OCR 读出来。
4. 示例文件全都有文字层，但验收时很可能用截图或扫描件来测。

#### 6.3.3 触发策略

| 情况 | 处理 |
| --- | --- |
| 图片文件 | 直接走 OCR |
| PDF 某页文字少于 20 个字，并且有图片或绘图内容 | 把这页渲染成 300 DPI 的图片，再走 OCR（判断为扫描页） |
| PDF 某页没有文字也没有图片 | 视为空白页，跳过（如销售合同第 3 页） |
| PDF 页面检测到印章 | 只把印章区域裁出来做 OCR（6.4） |
| Word、Excel 里嵌有图片 | 可选（默认关闭）：把图片提取出来走 OCR，结果作为辅助信息 |
| 文字层正常的 PDF、Word、Excel | 不走 OCR |

#### 6.3.4 引擎选型

| 方案 | 离线 | 中文效果 | 打包难度 | 结论 |
| --- | --- | --- | --- | --- |
| RapidOCR-Java（PP-OCRv4 + ONNX Runtime） | 是 | 好 | 低 | 采用，作为默认引擎 |
| Tesseract（Tess4J） | 是 | 中文一般 | 中 | 不采用 |
| PaddleOCR 原版（Python） | 是 | 好 | 高（要打包整套 Python 环境） | 不采用 |
| 云端 OCR 接口 | 否 | 好 | 低 | 不采用：文件要上传到外部服务 |
| Ollama 视觉模型（Qwen2.5-VL 等） | 是 | 很好 | 需要用户另外安装 | 作为可选的复核手段 |

#### 6.3.5 接口抽象与实现

OCR 功能统一通过 `OcrEngine` 接口调用，业务代码不直接依赖具体的 OCR 库：

| 方法 | 说明 |
| --- | --- |
| available | 引擎是否可用；原生库加载失败时返回 false |
| recognize（图片, 页码） | 识别一张图片，返回 Block 列表（来源为 OCR） |

`RapidOcrEngine` 的实现要点（接口已经用 `javap` 核对过，见附录 A）：

- 用 `InferenceEngine.getInstance(Model.ONNX_PPOCR_V4)` 获取单例，程序启动后懒加载。
- `runOcr` 只接受文件路径，所以先把 `BufferedImage` 写成临时 PNG，识别完再删除。
- `OcrResult.getTextBlocks()` 返回的每个 `TextBlock` 里有 `getText()`、`getBoxPoint()`（4 个角点）、`getBoxScore()`、`getCharScores()`。把它们转换成 `Block`：坐标按图片尺寸归一化；字号用框的高度近似；置信度取各字置信度的平均值。
- 参数：`ParamConfig.getDefaultConfig()`，再开启 `setDoAngle(true)` 和 `setMostAngle(true)`；`maxSideLen` 先用默认值，P0 阶段再调。

#### 6.3.6 预处理与后处理

| 阶段 | 处理 |
| --- | --- |
| 预处理 | 长边超过 2400px 时等比缩小；把红色和黑色分开，生成两张图：去掉红色的正文图、只保留红色的印章图；如有需要再纠正倾斜（P3） |
| 后处理 | 按 y 坐标把文字块聚成行，行内再按 x 排序；置信度低于 0.8 的块标记为“低可信” |
| 纠错 | 部门名用编辑距离和部门词典模糊匹配（如“财务郎”纠正为“财务部”）；日期用格式校验兜底；常见混淆字符（O/0、l/1）只在日期和编号字段里纠正 |

#### 6.3.7 并发、资源与降级

- 引擎是单例，用信号量限制并发数（默认 2）；PDF 按页渲染，每页识别完就释放图片。
- 原生库加载失败时，`available()` 返回 false：图片文件直接进入“待确认”，界面提示 OCR 不可用，其他功能照常运行，程序不崩溃。
- 备选方案：直接用 ONNX Runtime 1.22.0 加载 PaddleOCR 的 ONNX 模型自己实现；或者调用 Ollama 视觉模型。两者都实现同一个 `OcrEngine` 接口，可以随时替换。

### 6.4 区域切分与印章检测

#### 6.4.1 区域切分

| 区域 | 规则 |
| --- | --- |
| 标题区 | docx：第 1 页字号最大的连续段落（字号 ≥ 正文字号 + 2pt）；pdf 和 OCR：第 1 页上方 30% 范围内字最高的行；xlsx：没有标题行时用文件名去掉部门和日期后的部分；都找不到时用文件名 |
| 抬头字段区 | 标题之后、正文开始之前，形如“字段名：字段值”的行，如“合同编号”“甲方”“乙方”“签订日期”“编制部门”“编制单位”“编制日期”“会议时间”“主持人”“记录人” |
| 落款区 | 从文档末尾往上找，遇到“落款”“日期”“盖章”“审核人”“制表人”“记录人”“负责人”之一就向上扩展，最多 12 行；pdf 和 OCR 只看最后一页下方 50% |
| 正文 | 其余部分 |

#### 6.4.2 印章检测（P3 加分项）

1. 把页面渲染成 150 DPI 的图片（图片文件直接使用原图）。
2. 在 HSV 色彩空间里找红色像素：色相 ≤ 10 或 ≥ 170，饱和度 > 0.4，亮度 > 0.3。
3. 对红色像素做连通域分析，筛出外接框宽高比在 0.7–1.4 之间、面积占页面 0.3% 以上的区域，作为候选印章。
4. 把候选区域裁出来，只保留红色部分，交给 OCR 识别出盖章单位。弧形文字的展平（极坐标展开）放到 P3 再做。
5. 矢量印章（如采购合同）：PDFBox 能直接抽出章内文字，如果和红色区域的位置重叠，就直接使用这些文字。

输出 `SealInfo(page, box, text, confidence)`，写入台账的“盖章状态”和“盖章单位”两列。整个过程只用 Java 自带的 ImageIO，不引入 OpenCV。

### 6.5 字段识别引擎

#### 6.5.1 识别结果结构

每个字段（部门、类型、日期、标题）的识别结果包含：

| 项 | 说明 | 示例 |
| --- | --- | --- |
| value | 识别值 | `人力资源部` |
| confidence | 置信度，0–1 | `0.955` |
| evidence | 判断依据列表，按权重从高到低排列；每条包含信号名、原文片段、权重 | `FILENAME / 人力资源部_… / 0.85`；`KEYWORD_RULE / 任免 / 0.70` |

#### 6.5.2 部门识别

| 信号 | 权重 | 说明 |
| --- | --- | --- |
| LEARNED_RULE | 0.90 | 命中用户修正后生成的学习规则 |
| FILENAME | 0.85 | 文件名按 `_`、`-`、空格切开后，有一段是部门名或别名 |
| ANCHOR_FIELD | 0.85 | 锚点字段中出现部门名：编制部门、编制单位、发文部门、主办部门、落款、记录人、制表人、备案部门（如“报送至行政部备案”） |
| KEYWORD_RULE | 0.70 | 标题或正文命中“关键词→部门”规则（见下表） |
| TITLE_MENTION | 0.60 | 标题里出现部门名 |
| LLM | 0.60 | 大模型复核的结果（可选） |
| BODY_FREQ | 0.20 | 正文里出现次数最多的部门（容易受干扰，所以权重最低） |

合成方式：每个候选部门的得分 = 1 − ∏(1 − wᵢ)，也就是说多个信号同时指向同一个部门时，得分会叠加升高。取得分最高的部门；如果最高分低于阈值（默认 0.75），或者和第二名相差不到 0.15，就进入“待确认”。

默认的“关键词→部门”规则（可以在模板里修改）：

| 关键词 | 部门 |
| --- | --- |
| 任免、聘任、录用、考勤、薪酬、招聘、培训、绩效、离职 | 人力资源部 |
| 放假、值班、总经理办公会、行政、办公用品、会议室 | 行政部 |
| 决算、预算、财务、报销、审计、税务 | 财务部 |
| 销售合同、签约额、客户、回款 | 销售部 |
| 采购合同、框架合同、法律、诉讼、律师 | 法务部 |
| 安全生产、产能、车间、交付 | 生产部 |
| 研发、专利、样机、技术方案 | 研发部 |

规则按“长关键词优先”匹配，避免“合同”这种短词抢先命中。例如“销售合同”会先于“合同”匹配。

拿示例逐个验证：
- 任免通知：KEYWORD（任免）→ 人力资源部 0.70，加上文件名 0.85，合成得分 0.955。
- 只看内容不看文件名时，只有 0.70，低于阈值，进入待确认。这符合设计预期：信息不足时交给人工。

#### 6.5.3 日期识别

日期正则（全文清洗后再匹配）：

```text
(19|20)\d{2}\s*[-/.年]\s*(0?[1-9]|1[0-2])\s*[-/.月]\s*(0?[1-9]|[12]\d|3[01])\s*日?
```

| 优先级 | 来源 | 权重 |
| --- | --- | --- |
| 1 | 落款区里的“日期：”行 | 0.90 |
| 2 | 抬头锚点：签订日期、编制日期、会议日期、发文日期、印发日期 | 0.85 |
| 3 | 文件名中的日期 | 0.80 |
| 4 | 落款区里的其他日期 | 0.60 |
| 5 | 标题里的“2026年3月”这类年月（日期补为当月最后一天，标记为“推断”） | 0.40 |
| 6 | 文件元数据中的创建时间 | 0.10（只作参考，示例文件的元数据都是 2026-04-27） |

干扰词降权：日期前后 4 个字以内出现“至、起、止、前、截至、下次、定于、有效期、放假”时，这个日期的权重乘以 0.3。

合法性校验：年份在 1990 到当前年份 +1 之间，并且月、日是有效日期。
#### 6.5.4 文件类型识别

| 信号 | 权重 | 说明 |
| --- | --- | --- |
| LEARNED_RULE | 0.90 | 命中学习规则 |
| TITLE_SUFFIX | 0.80 | 标题以类型后缀结尾，如“……通知”“……会议纪要”“……合同” |
| FILENAME | 0.70 | 文件名里含有类型后缀 |
| CONTENT_FEATURE | 0.50 | 命中类型的内容特征（3.3 节类型表中的“内容特征”列） |
| TABLE_FEATURE | 0.50 | xlsx/xls 文件且表头含“合计、同比、人数、金额、率”等统计字段 → 报表 |
| LLM | 0.60 | 大模型复核结果（可选） |

后缀匹配取最长且最靠近结尾的那个。例如“工作总结暨 2026 年工作规划报告”以“报告”结尾，判为报告；“财务决算报表说明”中“报表”靠后，判为报表。合成方式和阈值与部门识别相同。

#### 6.5.5 标题识别

1. 取标题区文本（6.4.1），清洗后合并成一行。
2. 去掉模板里配置的前缀，例如公司名“XXX有限公司”（可配置是否去除）。
3. 去掉文件名命名规则中会重复出现的部分，例如标题本身以“通知”结尾、命名规则里又有 `{类型}` 时，不再重复。
4. 标题区为空时，用原文件名去掉部门段、日期段和扩展名后的部分作为标题。
5. 标题长度超过 40 个字时截断，完整标题保留在台账里。

#### 6.5.6 扩展字段

| 字段 | 来源 | 示例 |
| --- | --- | --- |
| 合同编号 / 文号 | “合同编号：”“文号：”或形如 `XX〔2026〕12号` 的文本 | `HC-CG-20251001001` |
| 甲方 / 乙方 | “甲方（……）：”“乙方（……）：” | `XXX有限公司` |
| 金额 | “合同总金额：人民币 X 万元” | `240万元` |
| 编制人 / 记录人 / 审核人 | 对应锚点字段 | `孙宇`、`赵文轩` |
| 关键词 | HanLP 提取正文关键词，取前 5 个 | `采购、元器件、质保……` |
| 页数、字数 | 解析器统计 | — |
| 是否盖章 / 盖章单位 | 印章检测（6.4.2） | `是 / XXX有限公司` |

扩展字段只写入台账，不参与命名规则，也不影响归档结果。

### 6.6 自定义 OA 模板

#### 6.6.1 模板内容

模板就是一份 JSON 配置，可以在界面里编辑，也可以导入导出。一份模板包含：

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| 公司名称 | 用于去掉标题前缀、识别落款单位 | `XXX有限公司` |

| 类型词典 | 类型名、代码、标题后缀、内容特征 | 3.3 节的 11 类 |

| 归档路径规则 | 归档目录的层级格式 | `{年}/{部门}/{类型}` |
| 档号规则 | 档号的格式 | `{年}-{部门代码}-{类型代码}-{序号4}` |
| 日期格式 | 命名中的日期写法 | `yyyy-MM-dd` |
| 置信度阈值 | 低于该值进入待确认 | 0.75 |

#### 6.6.2 占位符

| 占位符 | 含义 | 示例 |
| --- | --- | --- |
| `{部门}` / `{部门代码}` | 部门名 / 代码 | `人力资源部` / `RL` |
| `{类型}` / `{类型代码}` | 类型名 / 代码 | `通知` / `TZ` |
| `{标题}` | 识别出的标题 | `关于张明等同志职务任免的通知` |
| `{日期}` | 按日期格式输出的日期 | `2026-03-15` |
| `{年}` / `{月}` | 年 / 两位数月份 | `2026` / `03` |
| `{序号4}` | 4 位流水号（按年 + 部门 + 类型计数） | `0001` |
| `{档号}` | 按档号规则生成的档号 | `2026-RL-TZ-0001` |
| `{原文件名}` | 不含扩展名的原文件名 | `扫描件001` |

### 6.7 归档执行与撤销

#### 6.7.1 流程

1. 预览：为批次内每个“待归档”文件生成新文件名和目标路径，列出冲突（重名、路径过长、非法字符），等用户确认。
2. 执行：逐个文件处理。先写到目标目录下的临时文件，再原子重命名为正式文件名；完成后重新计算 SHA-256，与源文件比对。
3. 记录：每个文件写一条操作日志（批次、动作、源路径、目标路径、哈希、时间）和一条台账记录。
4. 撤销：按批次撤销。只删除哈希与日志一致的目标文件；如果是移动模式，把文件移回原位置。目标文件已被用户改过时不删除，提示用户手动处理。

#### 6.7.2 文件名与路径规则

| 问题 | 处理 |
| --- | --- |
| Windows 非法字符（反斜杠、斜杠、冒号、星号、问号、双引号、尖括号、竖线） | 替换成全角字符或下划线 |
| 首尾空格和点号 | 去掉 |
| Windows 保留名（CON、PRN、AUX、NUL、COM1–9、LPT1–9） | 末尾加下划线 |
| 重名、内容不同 | 末尾加序号：`…(2).pdf` |
| 重名、内容相同 | 不重复写入，标记为重复 |
| 完整路径超过 240 个字符 | 截断标题部分，完整标题保留在台账 |

#### 6.7.3 安全措施

- 默认复制，不动原文件；改成移动必须在模板里明确设置，界面上再弹窗确认。
- 归档根目录不能设为源目录或源目录的子目录，防止重复扫描。
- 程序只在归档根目录内写文件，不会删除归档根目录外的任何文件。撤销操作也只针对操作日志里记录过的文件。

### 6.10 启动器

启动器是程序的入口，负责让用户“双击就能用”：

1. 单实例检查：在数据目录写一个锁文件，里面记录当前端口。如果程序已经在运行，直接用浏览器打开已有的页面，然后退出。
2. 选择端口：默认 18080，被占用时依次尝试下一个端口，最多尝试 20 次。
3. 启动 Spring Boot：关闭 headless 模式（否则无法弹出选文件夹窗口和托盘图标），只监听 `127.0.0.1`。
4. 打开浏览器：启动完成后用系统默认浏览器打开首页。
5. 托盘图标：右键菜单包括“打开界面”“打开归档目录”“打开日志目录”“退出”。exe 不显示控制台黑窗口。

数据目录的位置：

| 情况 | 位置 |
| --- | --- |
| 程序目录可写（绿色版放在 D 盘、桌面等） | `<程序目录>\data\` |
| 程序目录不可写（如放在 Program Files） | `%LOCALAPPDATA%\OA-Archive-Agent\data\` |
| Docker | `/data`（挂载卷） |

默认归档根目录为 `%USERPROFILE%\Documents\OA归档\`，用户可以在界面上修改。

Docker 模式（环境变量 `OA_MODE=docker`）下不弹窗、不显示托盘、不打开浏览器，监听 `0.0.0.0`。

日志用 logback 按天滚动，保留 7 天，存放在 `data/logs/`。

### 6.12 规则自学习

- 触发条件：用户在“待确认”页修改了部门或类型，并点击“修正并学习”。
- 生成规则：从标题中提取 2–6 个字的关键词（HanLP 分词后，去掉停用词、部门名和类型名），生成一条“关键词 → 字段值”的规则，例如“产能达成 → 生产部”。
- 使用规则：识别时命中学习规则，产生权重 0.9 的 `LEARNED_RULE` 信号。
- 管理：学习规则会记录命中次数和最后命中时间，可以在模板设置页查看和删除。规则随模板一起导出。

## 7 数据模型

数据库为 H2 文件模式，连接串 `jdbc:h2:file:${oa.home}/db/oa;MODE=MySQL;AUTO_SERVER=FALSE`。开发阶段用 JPA 自动建表；发布前改为固定的 `schema.sql`，并加版本号，方便以后升级。

### 7.1 表结构

**archive_batch（批次）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | — |
| source_type | VARCHAR(16) | FOLDER / UPLOAD / INBOX |
| source_path | VARCHAR(1024) | 源文件夹路径（上传时为空） |
| target_root | VARCHAR(1024) | 归档根目录 |
| template_snapshot | CLOB | 模板 JSON 快照 |
| mode | VARCHAR(8) | COPY / MOVE |
| status | VARCHAR(16) | RUNNING / DONE / UNDONE |
| total / success / review / failed / duplicate | INT | 各状态的文件数 |
| created_at / finished_at | TIMESTAMP | — |

**file_record（文件处理记录）**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | — |
| batch_id | BIGINT FK | 所属批次 |
| original_path / original_name | VARCHAR | 源路径、原文件名 |
| work_path | VARCHAR(1024) | 工作区副本路径 |
| ext / size / sha256 / page_count | — | 文件基本信息 |
| status | VARCHAR(16) | 4.3 节的状态 |

| title / department / doc_type / doc_date | VARCHAR / DATE | 识别结果 |
| dept_conf / type_conf / date_conf | DOUBLE | 各字段置信度 |
| evidence_json | CLOB | 各字段的判断依据 |
| extra_json | CLOB | 扩展字段（合同编号、甲乙方等） |

| text_excerpt | CLOB | 清洗后的正文前 4000 字，用于预览和大模型复核 |
| new_name / target_path | VARCHAR(1024) | 预览生成的新文件名、目标路径 |
| corrected | BOOLEAN | 是否被人工修正 |
| error_message | VARCHAR(2000) | 失败原因 |
| created_at / updated_at | TIMESTAMP | — |

**archive_sequence（档号流水号）**

| 字段 | 说明 |
| --- | --- |
| seq_key | 联合键，形如 `2026-RL-TZ` |

**learned_rule（学习规则）**：`id`、`template_id`、`pattern`（关键词）、`field`（DEPARTMENT / DOC_TYPE）、`value`、`hit_count`、`last_hit_at`、`created_at`。

**process_step（处理步骤）**：`id`、`file_record_id`、`seq`、`step`（IMPORT / PARSE / OCR / RECOGNIZE / LLM / ARCHIVE）、`detail`、`duration_ms`、`created_at`。

### 7.2 表关系

```text
archive_batch 1 ── n file_record 1 ── 1 ledger_entry
                         │
                         ├── n process_step
                         └── n operation_log（同时关联 batch）
template 1 ── n learned_rule
```

| GET | `/api/templates/{id}/export` | 导出 JSON |
| POST | `/api/templates/{id}/naming-preview` | 用示例数据预览命名规则和路径规则的效果 |
| GET / DELETE | `/api/templates/{id}/learned-rules` | 学习规则列表 / 删除 |
| GET / PUT | `/api/settings` | 系统设置（大模型、默认目录等；apiKey 只写不读） |
| POST | `/api/settings/llm/test` | 测试大模型连通性 |
| GET | `/api/system/status` | OCR 是否可用、版本、数据目录、端口 |

### 8.4 安全说明

- 绿色版只监听 `127.0.0.1`，同一局域网的其他电脑访问不到，所以不做登录。
- `/api/ledger/{id}/open` 只能打开台账里记录过的文件，不接受任意路径。
- 所有接收路径参数的接口，都会先把路径规范化（`normalize` + `toRealPath`），拒绝包含 `..` 的路径。
- Docker 版默认也只映射到宿主机的 `127.0.0.1`。如果要开放给局域网，必须先增加访问密码（列为 P3 可选项），文档里会明确提示这个风险。

目标：执行一条 `mvn package`，前端自动构建并打进 jar，最后只得到一个 jar。

## 11 打包与部署

### 11.1 方式一：Windows 绿色版（主交付物）

#### 11.1.1 打包流程

`packaging/package.ps1` 依次执行以下步骤：

| 步骤 | 动作 | 产物 |
| --- | --- | --- |
| 1 | 检查 `JAVA_HOME` 是否为 Temurin 17 | — |
| 2 | `mvn -Pdist clean package`（含前端构建，跳过测试由参数控制） | `target/oa-archive-agent.jar` |
| 3 | 用 `jlink` 生成精简运行时 | `target/runtime/` |
| 4 | 用 `jpackage --type app-image` 生成程序目录 | `target/dist/OA-Archive-Agent/` |
| 5 | 复制使用手册、示例文件，创建空的 `data` 目录 | — |
| 6 | 压缩成 zip，并生成 SHA-256 校验文件 | `release/OA-Archive-Agent-v1.0.0-win64.zip` |

#### 11.1.2 jlink 精简运行时

初始模块清单（写在 `packaging/jlink-modules.txt`，P0 阶段实测后修正）：

```text
java.base, java.desktop, java.logging, java.management, java.naming,
java.net.http, java.prefs, java.scripting, java.security.jgss, java.sql,
java.xml, java.instrument, jdk.crypto.ec, jdk.localedata, jdk.unsupported,
jdk.zipfs, jdk.management
```

- `java.desktop`：选文件夹窗口、托盘、ImageIO 都要用到。
- `jdk.localedata`：中文日期和区域格式。
- `jdk.unsupported`：部分依赖库要用到 `sun.misc.Unsafe`。

参数：`--strip-debug --no-header-files --no-man-pages --compress=2`。

模块清单靠 `jdeps` 分析加实际运行来确认。如果某个依赖库在精简运行时上出问题，就退回到完整的 Temurin JRE，包会大约 40 MB，但功能不受影响。

#### 11.1.3 jpackage 参数要点

| 参数 | 值 |
| --- | --- |
| `--type` | `app-image`（不需要 WiX） |
| `--name` | `OA-Archive-Agent`（用英文名，避免中文程序名带来的编码问题；界面里显示中文名“OA文件智能归档智能体”） |
| `--input` / `--main-jar` | `target/` / `oa-archive-agent.jar` |
| `--runtime-image` | `target/runtime` |
| `--icon` | `packaging/app.ico` |
| `--app-version` | `1.0.0` |
| `--java-options` | `-Xmx1024m -Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8 -Djava.awt.headless=false` |
| `--win-console` | 不加（不显示黑窗口）；另外打一个带控制台的调试版，用于排查问题 |

#### 11.1.4 绿色版目录结构

```text
OA-Archive-Agent\
├── OA-Archive-Agent.exe        # 双击运行
├── app\oa-archive-agent.jar    # 包含前端页面、OCR 原生库和模型
├── runtime\                    # 精简的 Java 运行时
├── data\                       # 首次运行时生成：数据库、工作区、日志、设置
├── 使用手册.pdf
└── 示例文件\
```

预计 zip 大小为 150–200 MB（运行时约 50 MB，Tika 和 POI 约 60 MB，OCR 约 35 MB，HanLP 约 10 MB，其他约 20 MB），以 P0 实测结果为准。

#### 11.1.5 用户使用流程

1. 解压 zip 到任意目录（如 `D:\OA-Archive-Agent`）。
2. 双击 `OA-Archive-Agent.exe`，浏览器自动打开首页，托盘出现图标。
3. 选择要归档的文件夹，开始使用。
4. 退出：右键托盘图标，选择“退出”。

不需要安装 Java、数据库或任何其他软件，全程不需要联网。

#### 11.1.6 可选：正式安装包

安装 WiX Toolset 3.14（JDK 17 的 jpackage 不支持 WiX 4 及以上版本）后，把 `--type` 改为 `exe`，并加上 `--win-dir-chooser --win-shortcut --win-menu`，就能生成带安装向导、桌面快捷方式和开始菜单项的安装程序。本期先交付绿色版，安装包列为可选项。
### 11.2 方式二：Docker 一键部署（辅助交付）

#### 11.2.1 镜像设计

| 项 | 设计 |
| --- | --- |
| 构建方式 | 多阶段构建：第一阶段用 `maven:3.9-eclipse-temurin-17` 编译（含前端构建），启用 `docker` profile，引入 Linux 版 OCR 原生库；第二阶段只复制 jar |

| 访问范围 | 只能本机访问 | 默认只能本机访问 |

| D | 把 C 合成为没有文字层的扫描版 PDF，加上 2–3 张手机拍的文件照片 | 图片转 PDF；手机拍摄 | 验证扫描页的判断和 OCR |
| E | 异常文件：损坏的 docx、加密的 PDF、0 字节文件、`~$` 临时文件、超长文件名、带特殊字符的文件名、正被 Word 打开的文件 | 手工制作 | 验证“运行无崩溃” |
| F | 把 A–D 复制成 500 个文件 | 脚本复制 | 验证性能和稳定性 |

测试集放在 `src/test/resources/samples/`。每个文件的正确答案（部门、类型、日期、标题）写在 `expected.csv` 里，用于自动比对。

### 13.2 单元测试重点

| 对象 | 测试内容 |
| --- | --- |
| 日期识别 | 4 种日期写法；干扰日期降权；非法日期（如 2 月 30 日）被过滤 |

### 13.3 准确率目标

| 数据集 | 部门 | 类型 | 日期 |
| --- | --- | --- | --- |
| A（原始文件） | 100% | 100% | 100% |
| B（文件名无意义） | ≥ 90%，其余进入待确认，不允许静默识别错 | ≥ 90% | ≥ 90% |
| C、D（图片、扫描件） | ≥ 85%（目标值，P0 后根据实测调整） | ≥ 85% | ≥ 85% |

“静默识别错”是指识别结果错误、置信度却高于阈值的情况，这类错误要尽量为 0。识别不准时应该进入待确认，而不是直接归档到错误位置。

## 14 风险与对策

| 风险 | 可能性 | 影响 | 对策 |
| --- | --- | --- | --- |
| OCR 原生库在干净机器上加载失败（如缺 VC++ 运行库） | 中 | 高 | P0 阶段在虚拟机实测；需要的话把 DLL 放进 `runtime\bin`；OCR 不可用时降级，不影响其他功能 |
| RapidOCR-Java 自 2023-12 后没有新版本 | 中 | 中 | 封装在 `OcrEngine` 接口后面；备选方案是直接调用 ONNX Runtime，或使用 Ollama 视觉模型 |
| 扫描件和照片的识别准确率不够 | 中 | 中 | 预处理 + 词典纠错 + 置信度判断；识别不准就进入待确认，不静默出错 |
| 精简运行时缺模块，导致运行出错 | 中 | 中 | 用 jdeps 分析加实际运行验证；最坏情况退回完整 JRE |
| 包体积太大 | 低 | 低 | 只引入 Windows 版原生库；精简运行时；评估 Tika 中用不到的解析模块能否去掉 |
| Oracle JDK 再分发的许可问题 | 低 | 中 | 打包时使用 Temurin 17 |
| 评委电脑的端口被占用 | 低 | 中 | 启动器自动换端口 |
| 评委把程序放在 Program Files 等不可写目录 | 低 | 中 | 数据目录自动改到 `%LOCALAPPDATA%` |
| 文件被占用、文件名不规范 | 高 | 低 | 先复制到工作区再读；文件名清洗（6.7.2） |
| 误删、误移动用户文件 | 低 | 高 | 默认复制；只在归档根目录内写入；撤销前校验哈希 |
| 杀毒软件拦截未签名的 exe | 中 | 中 | 使用手册中说明处理方法；发布 SHA-256 校验值；有条件的话做代码签名 |
| `.wps`、`.et` 等 WPS 私有格式解析效果差 | 中 | 低 | P2 阶段验证；不能解析时只靠文件名识别并进入待确认 |
| 时效加分截止日期（2026-05-31）按本机日期已经过了 | 已发生 | 视赛事规则 | 以主办方最新通知为准 |

以下接口是从 Maven Central 下载 `rapidocr-0.0.7.jar`、`rapidocr-common-0.0.7.jar` 后，用 `javap` 查看的结果：

| 类 | 主要方法 / 常量 | 说明 |
| --- | --- | --- |
| `io.github.mymonstercat.Model` | `ONNX_PPOCR_V4`、`ONNX_PPOCR_V3`、`NCNN_PPOCR_V3` | 模型选择，本项目使用 `ONNX_PPOCR_V4` |

## 附录 B　术语表

| 术语 | 含义 |
| --- | --- |
| OCR | 光学字符识别，把图片中的文字转换成文本 |
| 文字层 | PDF 或 Word 中可以直接选中、复制的文字；扫描件没有文字层 |
| 锚点字段 | 形如“编制部门：销售部”的“字段名：字段值”文本，是识别的主要依据 |
| 落款区 | 文件末尾的署名、日期、盖章区域 |
| 置信度 | 识别结果的可信程度，取值 0–1 |
| 待确认 | 置信度低于阈值、需要人工确认的文件状态 |
| 档号 | 每份归档文件的唯一编号，如 `2026-RL-TZ-0001` |
| 台账 | 所有归档文件的目录清单 |
| 模板 | 部门词典、类型词典、命名规则、路径规则等配置的集合 |
| 学习规则 | 用户修正识别结果后，系统自动生成的“关键词 → 字段值”规则 |
| 绿色版 | 不需要安装、解压后就能运行的程序目录 |
| jlink / jpackage | JDK 自带的工具，分别用来生成精简运行时和生成 exe 程序目录 |
| SSE | Server-Sent Events，服务器向浏览器单向推送消息的技术 |
